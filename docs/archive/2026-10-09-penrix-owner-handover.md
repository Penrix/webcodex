**交接日期：2026-10-09**

## 一、先理解：我们究竟想做什么

我们要打造的不是一个新的 AI 编程工具，也不是把 ChatGPT 网页包装成另一种 Codex。

**我们真正要做的，是让 ChatGPT Web 从一个只能聊天、分析、提出建议的助手，变成一个能够使用用户真实电脑、持续完成实际工作的助手。**

用户现在面临一个根本性的割裂：

**ChatGPT Web 理解用户，Codex 能够执行任务，但两者之间缺乏连续、可靠的工作关系。**

用户与 ChatGPT 已经进行了大量长期讨论，涵盖软件开发、技术路线、男频网文创作、认知体系、自动化系统等项目。

这些讨论不只是简单的需求清单。

它们包含：

- 用户最初想实现什么；
- 为什么产生这个想法；
- 尝试过哪些路线；
- 哪些路线被否定，为什么；
- 某个问题经历了哪些认识转变；
- 目前真正认可的设计是什么；
- 哪些旧观点仍然具有参考价值；
- 哪些事情已经验证，哪些只是猜想；
- 用户现在到底希望软件产生什么效果。

ChatGPT Web 在持续对话中更容易理解这些内容。

但当任务交给本地 Codex 时，Codex 通常只收到当前的一段任务描述，以及仓库里有限的文档。

于是它容易出现一种情况：

**有很强的编程能力，却缺少对产品的完整认识。**

用户要的是一个真正能解决问题的软件；Codex 可能交付的是一个技术上符合当前任务合同、实际体验却不符合用户预期的实现。

这不代表 Codex 不够聪明。

恰恰相反，Codex 应当承担大量自主技术判断。问题在于，我们过去没有把足够完整的产品意图、认识形成史、当前状态和执行权责交给它。

WebCodex 就是为了解决这种割裂而被提到最高优先级。

## 二、最终产品是什么样子

请以一个普通使用场景理解终点。

用户正在 ChatGPT Web 聊天：

> “我们继续弄鼠标手势。上次那个右上角关闭窗口的问题还没解决，你去看看。”

理想情况下，ChatGPT 不应该回答：

> “好的，我帮你写一份任务合同，请复制到 Codex。”

而应该能够真正开始工作。

它能够：

1. 理解用户说的是哪个项目，以及此前为什么对那个功能不满意。
2. 找到真实代码仓库，检查当前实现，而不是凭记忆猜代码。
3. 使用本地工具查看文件、运行程序、修改代码、执行测试。
4. 读取真实运行结果，判断功能是不是已经达到用户想要的效果。
5. 如果发现问题，基于结果继续调整，而不是每次都让用户重新转述。
6. 将关键工作状态保留下来，之后换一个聊天窗口仍然能够继续。
7. 给用户一个真正可用的结果，并清楚说明哪些功能已经实测、哪些仍存在限制。

**用户需要面对的是一个能理解他、也能替他做事的 ChatGPT，而不是几个需要他亲自协调的 AI 工具。**

WebCodex 应尽可能承担执行工作，隐藏不必要的技术中转环节，同时保持实际操作、权限与结果可观察。

最终，用户使用 ChatGPT 自然语言提出目标，不再需要反复编写 GitHub Issue、复制复杂任务包、切换 Codex 窗口、人工传递日志。

技术上可以存在多个程序，但用户体验应该尽量接近一个连续工作的助手。

这就是我们所说的：

**让 ChatGPT 长出一双手。**

这里的“手”首先指代码、Git、文件、命令、测试和开发工具。未来可以扩展到其他本地操作，但不能假装现有 WebCodex 已经拥有所有桌面 GUI 或手机控制能力。

## 三、为什么选择 WebCodex，而不是继续强化 Codex 或 DSH

我们并非没有尝试过其他道路。

### 1. 最开始的工作模式：ChatGPT 出主意，Codex 写代码

这种模式证明了两件事：

第一，Codex 的实际编码能力很有价值。

第二，仅仅提高 Codex 的任务执行能力，并不能自动恢复用户与 ChatGPT 之间形成的长期认知。

过去我们不断增加任务合同、项目规范、审查规则，希望弥补 Codex 对真实意图的理解缺口。

这些规范确实有用，但始终存在一个问题：

**规范只能约束怎样执行，不能凭空补上没有传递过来的认识形成史。**

因此，新项目不应该继续把“编写更长任务合同”当成核心解决方案。

### 2. DSH 与 ChatGPT Web 浏览器桥接路线

我们尝试过让本地软件利用已登录的 ChatGPT Web 进行推理。

这积累了很多实际技术经验，包括：

- 浏览器登录态复用；
- 发送请求后的确认；
- 回复归属；
- 判断模型是否真正完成回答；
- 浏览器 DOM 变化；
- 长上下文；
- JSON 传输失真；
- 断线后无法确认是否已经发送；
- 本地转接服务与 Codex 配置冲突。

这些经验很宝贵。

但我们也遇到过真实问题，例如重复登录、回复解析失败、上下文过长、DSH 运行失败，以及浏览器桥接状态不可靠。

其中一个重要教训是：

**不要让一个浏览器桥接层同时负责推理、项目状态、任务管理、工具执行和记忆管理。**

它越承担不属于自己的职责，系统越难维护，也越难判断失败发生在哪里。

这些旧项目应该继续作为真实工程证据和可复用组件来源，但不必继续作为新系统的核心架构。

### 3. 为什么 WebCodex 更接近我们真正需要的底座

WebCodex 上游已经提供了很多实际开发工具能力：

- Project / Workspace；
- 文件读取和修改；
- Git 操作；
- 命令与测试执行；
- Server / Runner；
- Workflow Session；
- 长时间运行的 Job；
- Session 与 Job 的观察和恢复；
- 项目状态与执行证据。

这些是实际执行层应该拥有的能力。

因此，我们不应该再自己造一套任务系统、文件执行器、Job 管理器或者 Session 体系。

**WebCodex 应当作为真正负责工作执行的身体。**

而 ChatGPT Web 的接入层应该尽量薄，只解决如何让 ChatGPT 提出有根据的动作请求，并通过 WebCodex 执行、取得结果的问题。

这也是为什么我们决定以 `yyjeqhc/webcodex` 为底座，而不是重新开发一整套 Agent Runtime。

上游正在持续更新，Penrix Fork 应始终审查哪些能力已经由上游实现，避免重复维护。

## 四、系统中几个不同角色的关系

请不要混淆下面几个角色。

### ChatGPT Web：理解和判断

ChatGPT Web 承担与用户交流、恢复相关认知、理解产品目标、分析问题、决定下一步行动的职责。

它不是代码真相的拥有者。

当讨论涉及真实文件、程序状态和测试结果时，必须从执行层取得当前事实。

它的价值是将用户意图、历史认知与实际证据结合起来，而不仅仅是产生一段任务描述。

### WebCodex：真实执行与工作状态

WebCodex 承担工具调用、文件修改、命令运行、Git、执行权限、Session、Job 和真实结果的管理。

**执行事实以 WebCodex 和真实机器为准，而不是以模型声称自己已经执行为准。**

ChatGPT 负责判断可以做什么，WebCodex 负责按照授权真正去做，并提供可核对的结果。

### Codex：当前工程开发者，未来也可以是可选工作者

在 WebCodex 真正打通之前，本地 Codex 仍然承担建设 WebCodex 的工作。

请不要误解为我们想淘汰 Codex。

我们想改变的是默认协作关系。

当前由 Codex 负责工程实现、调试和技术选择。

未来 ChatGPT 能够通过 WebCodex 自主执行一部分开发任务后，Codex 仍然可以作为高价值的编码工作者参与复杂实现。

但不能要求用户为了每一个普通任务都手工启动一次 Codex、复制一遍上下文。

**最终系统不应依赖本地 Codex 每次都在线，也不应把 Codex 额度当作每次 ChatGPT Web 工具执行的必需成本。**

### ChatGPT Continuity：长期认知连续性

这部分和 WebCodex 有联系，但不是同一个项目。

WebCodex 主要解决：

> 我们正在做什么？真实代码和任务执行到哪里？能否继续执行？

ChatGPT Continuity 主要解决：

> 我们为什么在做这件事？过去怎样认识它？有哪些纠正、分歧、否定与重要发现？

一个负责工作连续性，一个负责认识连续性。

**二者最终需要协作，但不能把它们粗暴合并成一个庞大系统。**

## 五、最重要的区别：工作状态不等于认知记忆

这是整个项目容易走偏的地方。

假设某个 WebCodex Workflow Session 保存了：

- 项目名称；
- 当前任务；
- 已修改的文件；
- 最近运行过的测试；
- Git 状态；
- 下一步操作。

这对于恢复程序执行非常重要。

但是，如果用户之前说过：

> “右上角 Ctrl+W 是关闭当前窗口，不是只关闭 Chrome 标签。”

而这次纠正尚未写进项目代码或文档，那么新窗口即使成功恢复 Workflow Session，也未必知道这件事。

更进一步，用户的很多项目并不存在绝对、静态的“最终正确答案”。

尤其是长期的认知体系，过去的认识可能只是现在认识的另一个侧面，不应该一律标记为错误并覆盖。

所以用户接受的记忆原则是：

**我们保存的是 cognition trajectory，即认识怎样形成，而不只是 final truth，即当前总结出来的结论。**

在 `chatgpt-continuity` 中已经确立：

> OpenViking 负责成为记忆身体；Recorder 保存不可丢失的历史；Hot State 维持 ChatGPT 当前注意力；Selective Recall 只在必要时找旧材料；Cognition Trajectory 保存“我们是怎么走到这里的”；跨窗口 Rollover 最终承担真正的上下文压缩。

这套认知不要求 WebCodex 自己重新实现 OpenViking。

相反，它规定了未来连接记忆系统时必须遵守的边界。

尤其需要注意：

- 原始聊天和真实执行证据不能被摘要替代。
- 最近一次认识不一定绝对正确。
- 新认识不能自动消灭旧认识。
- 有价值的是变化关系，以及变化发生的原因。
- 不能假设“向量检索最相关的一个片段”就等于恢复了用户认知。
- 更好的上下文管理不是每轮都塞入更多原文，而是提供少量及时、足以续接当前任务的上下文。
- GitHub 负责长期知识与工程记录，但不应变成每轮聊天的记忆总线。

这些不是要求你马上开发一个复杂记忆系统。

它们是最终产品必须理解的语义约束。

请以 `chatgpt-continuity/docs/architecture/0003-cognition-continuity.md` 为当前详细认知来源，保留完整论证与形成过程，不要把它随意改写成一份简短的“记忆功能需求清单”。

## 六、一个特别容易被忽略的产品风险

当前 WebCodex PR #2 采用的方式，大致是：

```text
用户任务
   ↓
本地 Driver
   ↓
浏览器转接程序
   ↓
ChatGPT Web 作为 Planner
   ↓
输出一个待执行动作
   ↓
Driver 调用 WebCodex
   ↓
Windows 执行
   ↓
返回结果继续推理
```

这个设计作为技术验证是合理的。

但请注意我们的最终产品目标：

**用户希望的是他正在交流、已经积累大量认知的 ChatGPT 能够干活，而不是悄悄创建另一个不知道前因后果的 ChatGPT Planner。**

如果独立的 Planner 只收到一句任务和几段简短上下文，那么虽然它能操作电脑，本质上仍然重现了过去 Codex 缺少认知的老问题。

所以要明确区分：

**技术闭环成功：** 某个 ChatGPT Web 会话成功发出了工具调用。

**产品目标实现：** 用户真正正在使用的 ChatGPT 工作流程，能够携带必要认知，在正确的项目里持续执行任务。

前者是必要的工程基础，却不是后者的全部。

请调查当前 ChatGPT Web、官方支持的连接方式、浏览器中转能力与 Penrix 现有实现，在现实支持的权限和接口内寻找最合适的交互方式。

如果当前 Plus 网页环境不能直接让本聊天窗口使用自定义写入工具，就必须明确说明限制，选择可以落地的浏览器连接、上下文续接或其他受支持的方案。

不能把“另开一个无上下文的 ChatGPT 窗口进行自动操作”包装成最终产品已经实现。

也不要为了追求表面上的直接连接而绕过 WebCodex 的真实权限和执行边界。

## 七、用户实际想要的日常体验

用户使用 Windows 电脑，主要通过 Chrome 中的 ChatGPT Web 工作。

用户不是程序员，习惯使用自然语言表达目的。

不要以为用户愿意天天执行命令、阅读日志、手工编辑配置，或者参与普通的技术实现决策。

最终软件应该尽可能达到：

**启动方面：** 安装和配置应当简单，正常使用时不必反复登录 ChatGPT，不必每次手工启动多个终端服务；能够明确显示连接、执行、失败和恢复状态。

**工作方面：** 用户可以选择授权的本地项目，ChatGPT 能读文件、找问题、改代码、运行验证、查看结果，并与当前任务的历史状态保持一致。

**反馈方面：** 用户不需要看几十页终端输出才知道有没有成功。系统应将完成的行为、真实证据和仍未解决的问题清楚反馈。

**持续性方面：** 普通任务不能因为一个聊天窗口变长、关闭或切换就直接丢失工作状态。工作能够通过持久化的 Session 和 Job 机制恢复。

**认知方面：** 重要历史纠正、当前 Working 和拒绝过的路线可以由记忆系统提供，而不是要求用户反复解释。

**资源方面：** 用户的 Windows 电脑性能一般，不希望为了系统运行同时维护一大堆常驻程序、数据库、模型服务。

**成本方面：** 用户希望充分利用已有的 ChatGPT Web 使用能力，尽量降低本地 Codex 的日常消耗。不要为实现普通工具执行而默认增加新的付费模型依赖。

**可靠性方面：** 浏览器页面改版、登录状态变化、长时间运行任务和网络中断必须被当作真实问题，而不是只在理想单元测试里成立。

技术细节可以因现实条件调整，但不应该忘记这些使用体验。

## 八、过去反复踩过的工程问题

请特别理解这些经验背后的原因，而不是机械地把它们全部转化成新代码机制。

### 重复登录

过去曾经发生浏览器已有登录状态，却因为新流程不认识旧状态文件而要求用户反复登录的问题。

真正目标是稳定复用合法登录状态，而不是设计更多登录文件格式。

### 发送与执行状态不确定

请求发出去后断线，并不能证明没有执行。

如果某次修改文件的操作可能已经成功，就不应机械重试并制造重复副作用。

这需要可靠的执行证据与恢复能力，而不是简单增加重试次数。

### 过度防御和重复状态

LLM 特别容易因为担心失败而不断新增：

- 自己维护的重试表；
- 额外任务队列；
- 第二套 Session 状态；
- 影子 Job 记录；
- 重复权限规则；
- 多层兼容包装。

WebCodex 已经拥有真实的 Session、Job、权限和工具合同。必须优先复用它们。

**安全不意味着要无限增加状态机。真正可靠的方案往往是让一个真实组件拥有一项职责。**

### 用单测替代真实产品效果

此前多个项目存在“代码测试通过，用户实际使用还是不对”的情况。

WebCodex 的构建测试通过，不等于 ChatGPT 真正能够操作用户电脑。

即使执行闭环通过，也不等于用户日常工作入口已经好用。

要清楚地区分：

- 静态检查和单元测试；
- 云端 Windows 构建；
- 用户真实 Windows 实测；
- 日常使用体验；
- 长时间持续运行与恢复。

这些证据不能互相冒充。

### 把局部任务当作最终目的

过去用户经常被要求：

> 先做一次测试，等结果回来，再发下一份合同。

这种方法适合处理明确的不确定边界，但不适合作为整个产品的长期管理方式。

**你的工作不是等待 ChatGPT 每次给你一个新任务，而是主动理解并推进整个项目。**

请自己形成工程判断，自己安排合理顺序。

普通可解决的技术问题不需要反复交回用户。

只有涉及用户产品意图、不可逆操作、重大授权、安全或真实资源限制的决定，才需要请求用户。

即便这个闭环成功，也仍需确认怎样形成用户可以长期使用的工作入口，以及怎样将必要的当前认知带入执行会话。

所以：

**第一阶段已接近真实验收，不等于整个产品已接近完成。**

当前 Penrix Fork 使用已审查的上游 WebCodex 0.4.4 基线，上游已经发布 0.4.6 并继续开发。

版本升级由你根据当前源码、修复价值和验收风险自行判断。不要仅仅因为有新版就破坏已经积累的验证证据，也不要长期固守旧版而错过上游已修复的重要问题。

任何历史提交、版本号、PR 描述、测试结论，都需要对照当前真实仓库和用户机器状态核实。

## 十、明确的架构方向

建议保持下面这个职责关系：

```text
              用户
               │
         自然语言沟通
               │
               ▼
          ChatGPT Web
       理解、判断、决定行动
               │
         必要的认知恢复
               │
               ▼
         薄接入 / Provider
               │
               ▼
       WebCodex 官方运行时
        Project / Session
        Tools / Jobs / Runner
               │
               ▼
          Windows 电脑
       文件、Git、命令、测试
               │
         真实结果和证据
               │
               ▼
          ChatGPT 继续判断
```

旁边存在一套不同职责的连续性系统：

```text
ChatGPT Continuity
    │
    ├── Recorder：保留原始历史
    ├── OpenViking：记忆运行时
    ├── Hot State：当前注意力
    ├── Selective Recall：按需恢复历史
    ├── Cognition Trajectory：认识形成史
    └── Rollover：跨窗口上下文续接
```

这两套系统最终会有连接，但每套系统必须拥有清晰的职责。

不要因为需要传递一些记忆，就让 WebCodex 变成另一套大型记忆平台。

也不要因为记忆系统能够保存项目讨论，就让它代替 WebCodex 保存文件状态、Job 和执行事实。

最重要的是：**能力尽可能复用上游，Penrix 自己维护的差异尽可能薄。**

## 十一、哪些属于最终验收，而不仅仅是程序能运行

请用真实用户场景判断产品价值。

**场景 A：单次完整任务。**

用户提出一个普通软件修改需求。

ChatGPT 能找到正确项目，读取当前代码，修改并验证，再给出真实结果。

不需要用户在 ChatGPT 和 Codex 之间手工充当消息搬运工。

**场景 B：连续修改和纠偏。**

第一次结果不符合用户要求，用户直接说：

> “不是这个意思，我要的是整个窗口，不是浏览器标签。”

系统能够延续同一个实际工作对象，吸收这次产品纠正，查看刚才的修改，继续解决问题。

它不能每轮都像接到全新的孤立任务。

**场景 C：断线和恢复。**

浏览器连接中断、控制程序重启、执行任务还没有结束。

系统能够核实先前的执行状态，在安全情况下恢复任务，不重复已经发生的修改。

**场景 D：换窗口继续。**

一个聊天窗口已经很长或者不可用了。

新的 ChatGPT 工作窗口能够根据真实 Session / Job 状态恢复执行，并在记忆系统帮助下恢复继续判断所必需的产品认知。

这个场景不能通过无差别重放全部聊天历史来伪装成功。

**场景 E：真正可日用。**

用户能够在 Windows 上以相对简单、稳定的方式启动系统。

不必每次手动处理多套账号、配置、临时 Token、路径、环境变量和终端。

真实项目应具有适当的授权和权限边界，但普通操作不应该成为反复确认的仪式。

**场景 F：知道什么是真的。**

如果文件确实改了、测试确实通过，系统可以说明。

如果只是模型建议了修改、工具没有执行，系统必须明确说明。

如果结果未知，不能冒充成功。

只有这些场景得到适当的真实验证，才有资格声称用户真正获得了一个可工作的 ChatGPT 执行环境。

## 十二、你作为 Codex 拥有什么自主权

这部分非常重要。

用户不是要求你按照一份细碎的施工清单机械执行。

**你是这个项目当前的工程负责人。**

你可以自主决定：

- 当前应该先审查哪些代码；
- 选择哪些上游能力而不是重新实现；
- 是否存在更好的 Provider 接入方式；
- 如何安排构建、测试和真机验证；
- 哪些旧实验代码已经没有存在价值；
- 怎样减少当前 Driver 的复杂度；
- 如何改善安装、登录态复用和日常启动体验；
- 哪些错误需要调试，哪些路线应该停止；
- 哪些关键认知需要写入长期项目文档。

但是，有几个不可自行改变的产品方向：

1. **核心目标始终是让 ChatGPT Web 获得实际执行能力。** 不能悄悄退化成“帮用户自动生成给 Codex 的 Prompt”。

2. **用户的历史认知与当前意图必须得到尊重。** 不能把只有当前任务描述的独立 Planner 直接等同于已经理解用户的 ChatGPT。

3. **不重复建设上游已经拥有的系统。** WebCodex 管执行，OpenViking 管记忆，Recorder 管原始证据。

4. **真实使用效果比漂亮的实现说明重要。** 未在真实场景验证的功能不得写成完成。

5. **用户不承担普通技术选择责任。** 能调查、能判断、能解决的问题由你自主处理。

6. **保护已有用户状态。** 不擅自清空浏览器记录、覆盖登录状态、丢弃项目变更、重写 Git 历史或重复执行结果不明的操作。

7. **重要产品认知应当进入可发现的仓库文档。** 不能只存在于聊天窗口、PR 评论或短期任务合同里。

除此以外，不需要为了满足旧任务合同而坚持明显不合理的技术路线。

任务合同是工作材料，不是现实本身。

## 十四、现在交给你的不是一个小任务，而是整个项目

请正式接管 Penrix WebCodex 的后续工程推进。

如果某个发送或文件操作的结果存在无法判定的副作用风险，应先停止重复操作，核实状态。这是必要的正确性边界，不是要求你停止整个工程思考。

涉及账号登录、真实项目的重要修改、不可逆清理、额外付费或授权扩大时，遵守实际权限要求；不要替用户做未授权的外部操作。

在工程推进中，及时维护当前产品方向、真实实现状态与重要认识变更，使未来的新 Codex 会话也能接手，而不是再次从零理解。

用户不是想管理一个越来越庞大的 AI 自动化基础设施。

最终我们期待的是：

**ChatGPT 理解我们，记得我们，能够亲自动手，并能把事情持续做完。**

WebCodex 是实现这件事的关键执行基础设施。

请围绕这个产品目标自主推进，而不是围绕任何一份临时任务合同优化。
